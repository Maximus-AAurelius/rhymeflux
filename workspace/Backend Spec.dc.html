BARWORK — BACKEND SPECIFICATIONv1 · SEPT 2026

Barwork backend specification

What the client already does, what has to move server-side, and the order to build it in. The prototype is a working reference implementation of the hard part — the rhyme engine in rhyme-engine.js is the algorithm, not a mock, and the service below is that file promoted to a real dictionary and a cache.

CLIENT KEEPS
Typing, colouring, syllable counts, beat grid, recording
SERVER OWNS
Songs, sync, dictionary, AI, entitlements, audio storage
HARD CONSTRAINT
Writing must work fully offline; nothing blocks a keystroke

1. Architecture

Four services behind one gateway. The split is drawn on latency budget: anything a keystroke can trigger has to answer in under 50 ms or run locally.

2. Data model

A bar is the unit of everything — colouring, syllable counts, takes and AI all address a bar. Store bars as rows, not as a text blob: the beat grid, per-bar takes and per-bar AI history all need a stable id, and a blob forces a full-document diff on every keystroke.

users            id, email, display_name, accent (default 'us'), created_at
subscriptions    user_id, tier ('free'|'pro'), period_end, store_receipt, ai_used, ai_period_start
folders          id, user_id, name, position
songs            id, user_id, folder_id, title, bpm, time_sig (default '4/4'),
                 beat_asset_id, updated_at, deleted_at, rev (bigint)
sections         id, song_id, kind ('verse'|'hook'|'bridge'|'intro'|'outro'),
                 label, position
bars             id, section_id, position, text, syllables (int, cached),
                 updated_at, rev
takes            id, bar_id, user_id, asset_id, duration_ms, created_at
assets           id, user_id, kind ('take'|'beat'), s3_key, bytes, peaks (jsonb),
                 status ('pending'|'ready'|'failed')
ai_events        id, user_id, song_id, lane, kind ('next_bar'|'rewrite'|'verse'),
                 prompt_hash, accepted bool, tokens, created_at
sync_log         id (bigserial), user_id, entity, entity_id, op, payload jsonb, rev

Notes: rev is a per-user monotonic counter (Postgres sequence) — the client stores the highest rev it has seen and pulls deltas above it. Soft-delete songs; hard-delete bars. syllables is a cache the server recomputes on write so the library can show flow stats without loading text.

3. API surface

ENDPOINTBEHAVIOUR
POST /v1/syncThe only write path. Body: {since: rev, ops: [...]}. Returns applied revs plus every op above since. Idempotent on client-generated op ids.
GET /v1/songsLibrary rows: title, bpm, bar count, avg syllables, take count, first bar, updated_at.
GET /v1/songs/:idFull document — sections, bars, takes, beat asset.
GET /v1/rhymes?q=&tier=&pool=&limit=tier one of perfect / family / slant / assonance; pool words or phrases. Returns {word, score, tier, syllables, phonemes} ranked. Cacheable 24 h, ETag on dictionary version.
POST /v1/analyzeBody {lines[], sensitivity}. Returns syllable counts and rhyme-family assignments per token. Server-authoritative version of the client's local pass; used for imported text and cross-device consistency.
POST /v1/ai/next-barBody {song_id, lane, context_bars, target_syllables, lock_word}. Streams candidates; each is verified against lock_word before it is emitted, and unverified lines are labelled, never silently shipped. Decrements quota on accept, not on generate.
POST /v1/ai/rewrite · /verseSame contract; /verse is Pro-gated and returns 402 with the entitlement payload when free.
POST /v1/takes/upload-urlSigned PUT for the raw recording. Client uploads direct to S3; worker transcodes and writes peaks, then the take flips to ready over the sync channel.
GET /v1/entitlementsTier, AI actions remaining, per-song take cap, free-tier colouring cap. Client renders every gate from this, so limits change without a release.

Auth is bearer JWT, 15-minute access token with a rotating refresh token. Rate-limit /rhymes generously (it fires on every word tap) and /ai/* tightly.

4. Rhyme service

Port rhyme-engine.js as-is; it already exports the full surface — getRhymes, getSyllableCount, score, verifyRhyme, rhymeFamilies, registerSlang. Four changes turn the prototype into the service:

01
Real dictionary. Swap the curated lexicon for CMUdict (~134k entries) loaded into memory as a prefix-keyed map; keep the grapheme-to-phoneme fallback for anything missing, which is what makes slang and coined words work at all.
02
Inverted rhyme index. Scoring every candidate pairwise is O(n) per query and fine at 400 words, not at 134k. Key each entry by its rhyme tail (last stressed vowel onward) and by vowel nucleus; a query scores only its two buckets, then ranks.
03
Redis where the Map is. The engine's in-process cache is already isolated behind one accessor. Key on word|tier|pool|dictVersion so a dictionary bump invalidates cleanly.
04
Slang as data. slang-overlay.json becomes a table with an editorial review flag, hot-reloaded on a version bump. This is the file that needs a submission path from users eventually.

Ship the same module to the client as a WASM or JS bundle with a trimmed 20k-word dictionary, so colouring and counting keep working with no network. The server pass is the authority; the client pass is the one that has to be instant.

5. Offline and conflicts

Writing is single-author, so full CRDTs are overkill. Bars are addressed by client-generated UUID and ordered by fractional position keys, which makes insert and reorder commutative — the two operations that would otherwise collide. Resolution is last-write-wins per bar on updated_at, with the loser retained in sync_log so a "restore this version" screen is possible later. Takes never conflict: they are append-only and immutable.

6. Billing and gates

StoreKit 2 and Google Play Billing, verified server-side; the receipt is the source of truth and subscriptions is a cache refreshed on webhook. Every limit in the paywall screen is a server value: colouring cap (12 bars free), AI actions (15 free / 500 Pro, reset on ai_period_start), takes per song (3 free), full-verse generation (Pro only). Enforce all four server-side and treat the client checks as UI only.
